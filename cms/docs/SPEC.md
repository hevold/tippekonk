# Desken — specification and engineering contract

Desken is a flexible, production-grade content management system for small
Norwegian newsrooms (lokalaviser, nisjemedier, fagblad). It replaces the
"WordPress with 40 plugins" setup with one coherent, fast, secure system that
understands how a Norwegian newsroom works: desk workflow, bylines, sections,
front-page editing, plus-articles, live blogs, Vær Varsom-plakaten, and
Norwegian language everywhere.

This document is the contract shared by everyone building it. Read it fully
before writing code. When this document and your training data disagree
about Next.js 16, the bundled docs in `node_modules/next/dist/docs/` win.

## 1. Quality bar

"AAA" means:

- It works end to end. Every feature is reachable from the UI, persists, and
  survives a reload. No placeholders, no "TODO: implement", no mocked data in
  production paths.
- It is correct under concurrency and failure: optimistic locking on saves,
  edit locks with heartbeat, idempotent scheduler, retries with backoff.
- It is secure by default: argon2id, httpOnly cookies, CSRF-safe actions,
  permission checks in every server action and route handler, no raw HTML
  from user content, upload sniffing, rate-limited login.
- It is accessible: WCAG 2.1 AA. Keyboard-operable admin, focus management in
  dialogs, labels on every control, `aria-live` for autosave status, colour
  contrast ≥ 4.5:1, reduced-motion respected.
- It is fast: public pages render from cached queries, images are responsive
  WebP with `srcset`, no client JS on public pages except where interactive
  (live blogs, search, menu). Admin uses server components by default.
- It is Norwegian: all UI copy is bokmål (nb) via i18n, dates use
  `Europe/Oslo` and `nb-NO`, slugs transliterate æøå, search uses the
  Postgres `norwegian` configuration.
- It is tested: unit tests for pure logic, integration tests for services
  against a real (embedded) Postgres, end-to-end tests for the core editorial
  flow.
- It is documented: every module has a header comment saying what it is for;
  the README lets a newsroom's IT-savvy journalist install it in 15 minutes.

### 2.1 Next.js 16 facts that differ from older training data

- `cookies()`, `headers()`, `draftMode()`, `params`, `searchParams` are all
  **async** — `const { id } = await params`. Use the generated helpers
  `PageProps<'/admin/artikler/[id]'>`, `LayoutProps<'/admin'>`,
  `RouteContext<'/api/x/[id]'>` (run `pnpm exec next typegen` if missing).
- Middleware is `src/proxy.ts` exporting `proxy(request)`; it runs on the
  Node.js runtime. Keep it cheap (cookie presence checks, header injection).
- `revalidateTag(tag, 'max')` takes two arguments. `updateTag(tag)` in server
  actions for read-your-writes. `refresh()` from `next/cache` refreshes the
  router from an action. Cache Components are **not** enabled; use
  `unstable_cache` via `cachedPublic()` in `@/server/cache.ts`.
- Do not use `next/image`; use `<MediaImage>` from `@/components/media/media-image`.
- Route handlers: `export async function GET(request: Request, ctx: RouteContext<'/api/...'>)`.
- Server functions: `'use server'` at the top of files under `src/server/**/actions.ts`.
- `next dev` writes `AGENTS.md`/`CLAUDE.md` managed blocks — leave them.
- Read `node_modules/next/dist/docs/01-app/01-getting-started/*.md` for anything else.

### 2.2 Environment available while building

- A real PostgreSQL 16 runs at `postgres://postgres@127.0.0.1:5433/desken_dev`

Ownership rules:

- You may create and edit files only in the areas you own, plus your own
  i18n message file `src/lib/i18n/messages/nb/<area>.ts`.
- Shared registries (`admin-nav.ts`, `routes.ts`, `messages/nb/index.ts`,
  `schema.ts`, `package.json`) are frozen. If you truly need a schema change,
  add columns in a **new** migration via a new schema addition and
  `pnpm db:generate`; never rewrite `drizzle/0000_init.sql`. If you need a
  dependency that is not installed, `pnpm add <pkg>` is allowed, but prefer
  what is already in `package.json`.
- Never run `git` commands. The orchestrator commits.
- Never delete or rewrite another area's files. If you need something from
  another area that does not exist yet, write against the interface in this
  document and leave a clear `// INTEGRATION:` comment where it plugs in.

## 4. Architecture

### 4.1 Request flow

- `src/instrumentation.ts` (`register()`), on the Node.js runtime only:
  `await getDb()`, run migrations when `AUTO_MIGRATE`, `startScheduler()` when
  `ENABLE_INTERNAL_SCHEDULER`.
- `src/proxy.ts`: for `/admin/**` except `(auth)` routes, redirect to
  `/admin/login?next=...` when the session cookie is absent (optimistic check
  only; real verification happens in `getAdminContext()`). Sets
  `x-pathname` header for layouts.
- Admin pages are dynamic. Every admin page starts with
  `const ctx = await getAdminContext()` (redirects to login if needed) and
  checks `ctx.can('...')` before rendering privileged UI.
- Public pages resolve the site from the `host` header with
  `getPublicSite()` (cached per request with React `cache()` and in-memory
  for 60 s), fall back to the default site (first active site) for unknown
  hosts, and read through `cachedPublic()` wrappers.

Resolution rules: walk rows top-to-bottom, blocks left-to-right; pinned

### 4.9 Public API v1 (`/api/v1/**`, owner: integrations)

Authentication: `Authorization: Bearer <key>` (API keys) or none for public
read of published content? — **Decision:** the API always requires a key
(newsrooms decide who consumes it). Responses are JSON `{ data, meta }` with
`Cache-Control: private, max-age=30`. Errors `{ error: { code, message } }`.

- `GET /api/v1/articles?section=&tag=&q=&page=&per_page=&since=` → teasers
- `GET /api/v1/articles/:id` → full article incl. `body` (ContentDoc) and `html`
- `GET /api/v1/sections`, `GET /api/v1/tags`, `GET /api/v1/authors`
- `GET /api/v1/live/:slug` → live blog with posts
- `GET /api/v1/site` → name, settings.theme, menus
- CORS: `Access-Control-Allow-Origin: *` for GET.

Webhooks: events `article.published`, `article.updated` (published article
saved), `article.unpublished`, `layout.published`, `live.post_created`.
Payload `{ id, event, createdAt, site: { id, slug }, data: {...} }`, header
`X-Desken-Signature: sha256=<hmac hex>` over the raw body, `X-Desken-Event`.
Delivery: enqueue rows in `webhook_deliveries`; scheduler delivers with
backoff 1 min × 2^attempt up to 8 attempts; UI shows deliveries per webhook
with "send på nytt".

## 5. Domain rules

### 5.1 Roles and permissions

See `src/lib/permissions.ts`. Key rules:

- Contributors can only open/edit articles they created (`createdBy`).
- Journalists can edit all articles but cannot publish; they move articles to
  `in_review` ("Send til desk").
- Editors and admins publish, schedule, unpublish, and edit layouts.
- Every server action and route handler calls `requirePermission()` or
  checks `ctx.can()`; UI hiding is never the only check.
- Superadmins (`users.isSuperadmin`) act as admin on every site and can
  create sites.

### 5.2 Workflow transitions

```
draft → in_review → approved → published
draft/in_review/approved → scheduled → published (by scheduler)
published → unpublished → draft/published
any → archived (published articles must be unpublished first)
any (except published) → trash (deletedAt) → restore
```

Norwegian labels: Utkast, Til gjennomsyn, Godkjent, Planlagt, Publisert,
Avpublisert, Arkivert, Papirkurv. Transition buttons in the editor show only
what the role allows; the service enforces the state machine.

### 5.3 Slugs and URLs

- Article slug generated from the title on first save with a non-empty
  title; editable; unique per site (`uniqueSlug`). Reserved words rejected
  for section slugs only.
- Canonical article URL: `/{section.slug}/{article.slug}`; when the article
  has no section: `/a/{id}`. `/a/{id}` always 301s to canonical.
- When the slug or section of a **published** article changes, insert a
  redirect from the old path to the new one (`redirects` table). The public
  `[section]/[slug]` route consults redirects before 404.

### 5.4 Publish validation (`validateForPublish`)

Errors block publishing; warnings are shown but allowed:

- title required, ≤ `settings.editor.titleMaxLength` (warning above)
- lead required when `settings.editor.requireLead`
- section required
- at least one byline
- featured image required when `settings.editor.requireFeaturedImage`
- every image used (featured + body) must have `alt` (error) and `credit`
  (warning)
- sponsored articles must have `isSponsored` label acknowledged (warning)
- checklist: when `settings.checklist.enabled`, all `required` items must be
  ticked (stored in `articles.flags` as `checklist:<id>: true`)
- scheduledAt in the past → error

### 5.5 Revisions and locks

- Every manual save creates a revision (`kind: 'manual'`, incrementing
  `version`). Autosaves create `kind: 'autosave'` revisions at most once per
  60 s; only the last 20 autosaves per article are kept. Publishing creates a
  `'publish'` revision; restoring creates `'restore'`.
- `saveArticle` rejects with `ConflictError` if `expectedVersion !==
  article.version` (someone else saved). The editor then offers "Last inn på
  nytt" and shows who saved.
- Locks: opening the editor acquires a lock; heartbeat every 30 s; a lock
  older than 90 s is stale and may be taken over. Read-only mode with a
  banner ("Kari Nordmann redigerer denne saken") when locked by someone else.

### 5.6 Plus (paywall)

`articles.access = 'plus'` and `settings.paywall.enabled`: the public article
page renders the first `teaserParagraphs` paragraphs and a CTA box; the full
body is not sent to the client. Feeds contain the lead only. `plus` articles
carry a "Pluss" label on teasers. (Subscription/identity systems are external;
`settings.paywall.loginUrl` links out.)

### 5.7 Live blogs

`live_blogs` with status draft/live/ended, posts ordered newest first, pinned
posts on top, key events listed in a summary box. Public page polls
`/api/live/[id]/posts?after=<iso>` every `settings.live.pollIntervalSec`
seconds. Admin composer posts with the same editor in compact mode.

### 5.8 Multi-site

A single installation hosts several titles. `sites.domains` maps hosts.
Users have one membership per site. The admin topbar has a site switcher
(cookie `desken_site`). Everything in the admin is scoped to `ctx.site`.
Seeds create one site; the settings area lets superadmins create more.

- Server components only, except `MenuToggle`, `SearchForm`, `LiveFeed`,

- Theme from `settings.theme` → CSS variables on `<html>`:

  and updated timestamps (`<time datetime>`), featured image with caption and
  credit, body via `renderDoc`, tags, related articles, "Les også" from the
  same section, paywall teaser when plus, sponsored label when
  `isSponsored` ("Annonsørinnhold"), breaking badge, print stylesheet.
- SEO: `generateMetadata` with title suffix, description, canonical, OG/Twitter
  tags with featured image, `robots noindex` when `noIndex`,
  `NewsArticle` JSON-LD (headline, datePublished, dateModified, author,
  publisher with logo, image, articleSection, isAccessibleForFree), `BreadcrumbList`,

  no layout shift (aspect ratio boxes), fonts self-hosted with `font-display: swap`.
- Accessibility: landmarks, skip link, one `h1`, focus styles, `lang="nb"`.
- Pageviews: article page includes `<PageviewBeacon articleId/>` (tiny
  client component, `navigator.sendBeacon('/api/beacon')`), counted per day.

## 8. Testing conventions

- Unit tests next to code: `foo.test.ts`. Run with `pnpm test`.
- Database tests: `const db = await useTestDb()` from `@/test/db` in
  `beforeAll` — creates an in-memory PGlite DB, applies migrations, calls
  `setDb()`. `seedMinimal(db)` returns `{ site, admin, editor, journalist, contentType, section }`.
- Service tests exercise real logic (create → save → publish → query).
- E2E (`e2e/*.spec.ts`): global setup migrates + seeds `./data/e2e-pglite`
  and builds; specs log in as the seeded editor, create an article with the
  editor, upload an image, publish, and assert the public page, feed and
  sitemap. Selectors use roles and labels, not CSS classes.
- Before declaring done, each area runs `pnpm typecheck && pnpm lint &&
  pnpm test` and fixes everything it introduced. The orchestrator runs
  `pnpm build` between phases.

## 9. Coding standards

- TypeScript strict; no `any` (use `unknown` + narrowing); no `@ts-ignore`.
- Validate every boundary with Zod: action inputs, route handler bodies,
  search params, JSON columns when read from DB if user-editable.
- Server code that must never reach the client imports `'server-only'`
  (except `src/db/*` and `src/env.ts`, which scripts import).
- Errors: throw the `ActionError` subclasses from `@/server/actions`; user-facing
  messages in Norwegian; log with `console.error('[area]', err)`.
- Every mutation: permission check → validate → transaction where multiple
  rows change → audit → notifications → cache revalidation → return.
- No secrets in code. Read config via `env` from `@/env`.
- Files: kebab-case; React components PascalCase exports; one default export
  per page/layout only.
- Comments explain *why*; module header comments explain *what for*.
- Norwegian in UI, English in code and comments.
- Prettier formatting (`pnpm format`) before finishing.
